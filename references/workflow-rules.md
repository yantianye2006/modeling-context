## 1. 外部工作记忆

把建模目录视为项目状态库，而不是素材仓库或论文草稿。它应持续回答：

- 题目要求什么，各问如何传递输入、模型和结论；
- 哪些内容是题面或数据事实，哪些只是暂定假设；
- 为什么选择、修改或淘汰某个模型；
- 当前结论由哪些数据、代码、结果和验证支持；
- 上游变化会使哪些下游内容失效。

不要把所有内容堆入一个 Markdown。总览负责导航，专题文件负责事实和口径，分析卡负责单问状态，日志负责变更原因，项目设计总览负责稳定后的最终主线。

## 2. 信息类型与状态

本节是整个 skill 的状态与证据规范源。`SKILL.md`、模板和脚本只能使用这里的枚举与进入条件，不得另建同义状态。新生成但尚未填写的骨架统一使用 `stage: problem-framing`、`status: draft`。

| 类型 | 定义 | 可接受证据 |
| --- | --- | --- |
| 事实 | 题面、附件或可靠来源直接支持的信息 | 题面位置、原始数据、可靠文献 |
| 假设 | 为建模暂时采用、仍需验证的判断 | 理由、风险、验证计划 |
| 决策 | 在多个可行方案间作出的选择 | 比较结果、约束、明确理由 |
| 结果 | 可复现计算或检验产生的输出 | 代码、参数、结果表、运行记录 |

核心文件使用以下 Properties：

```yaml
stage: problem-framing | analysis | implementation | validation | writing
status: draft | active | validated | superseded
question: 1 | 2 | 3 | global
depends_on: []
feeds_into: []
updated: YYYY-MM-DD
```

`stage` 和 `updated` 不是装饰字段：每次修改文件时都按实际进度推进 `stage`、刷新 `updated`，否则按 stage 路由最小上下文的机制会失效。各值的进入条件与推进责任：

| stage | 进入条件 | 由哪种模式推进 |
| --- | --- | --- |
| problem-framing | 文件已创建，问题框架尚未写完 | 初始化 |
| analysis | G0 已通过，问题框架、数据事实和统一口径足以开始 G0.5 结构诊断 | 初始化 / 结构诊断 / 分析更新 |
| implementation | G0.5 与 G1 已通过，交给正式实现阶段 | 分析更新 |
| validation | 结果已回填，主模型已通过预设判据 | 结果回填 |
| writing | 论文前门禁已通过，结论与图表已冻结 | 项目收敛 / 论文交接 |

`stage` 表示流程进度，`status` 表示内容是否为当前有效版本，两者不得互相替代：

| status | 使用条件 |
| --- | --- |
| draft | 新建骨架、字段未填完；只用于 `problem-framing` |
| active | 当前采用且已满足所在 `stage` 的必填要求 |
| validated | 当前采用，并已有可复现证据通过预设判据 |
| superseded | 已被新版本或新决策替代；保留历史但不得作为当前输入 |

**`stage` 与 `status` 的兼容表**（`superseded` 是历史标记，不受本表约束，可出现在任何 `stage`）：

| stage | 允许的 status |
| --- | --- |
| problem-framing | `draft`、`active` |
| analysis | `active`、`validated` |
| implementation | `active`、`validated` |
| validation | `validated` |
| writing | `validated` |

这张表的作用是防止 `stage` 虚假推进。推进 `stage` 本身就是一次断言——上表「进入条件」已经满足；内容还没达到该 stage 的进入条件就不该推进，而不是推进之后用 `draft` 兜底。因此**离开 `problem-framing` 后不再有 `draft`**：推进 `stage` 时必须同时把 `status` 提到该 stage 允许的值。G0 通过后进入 `analysis`，G0.5 尚未完成由 gate 的 `not-checked` 表达，不再退回文件级 `draft`。

`validation` 与 `writing` 只允许 `validated`：这两个 stage 的进入条件本身就要求已有可复现证据通过预设判据，此时 `active` 与 `validated` 的区别已经消失。

**手写状态字段允许附加说明。** 表格与条目里手写的状态值（交付物条目 `status`、`kind`，预算表的级别与状态，要求—证据追踪的状态，参数/角点/负结果三个自检字段，负结果的闭环处置）都只按**前导状态词**判定，后面可以跟括注或简短说明，例如 `passed（三种子 5 折重复）`、`planned 待实现`。状态词后必须是非字母数字分隔符，因此 `not-checked（实现阶段执行）` 仍然按未完成处理，不会被误判为已完成。frontmatter 中的 `stage`、`status` 和 gate 记录不适用本条，必须写纯枚举值。

门禁记录中的 `status` 是检查结论，不是文件级 `status`，不得把两套枚举混用。GP/G0/G0.5/G1–G3 的作用与通用状态语义以 `SKILL.md`「Stage 与 gate 总表」为准，推进动作以 `pipeline.md` 对应步骤为准；本节只规范文件状态，不复制门禁条款。

`scripts/validate_modeling_context.py` 按本表检查（`E_STAGE_STATUS`）。检查器与本节不一致时以本节为准，修改检查器。

上面的 status 表约束的是**文件 frontmatter 的 `status`**。交付物条目（`交付物清单.md` 中的单条；旧项目兼容 `图表清单.md`）另有一套成熟度枚举 `planned | drafted | active | superseded`，定义在交付物清单内，描述单个交付物而非文件的流程阶段；两套不得互相套用，条目升 `active` 也不改变所在文件的 `status`。

问题卡的 `stage` 只反映本问进度。`项目设计总览` 等全局文件的 `stage` 取各问的最低值，不因某一问完成而提前推进。同一事实在多个文件中的状态描述必须一致：把某个条目升为 `active` 时，一并检查引用它的分析卡、总览与索引是否仍写着旧状态。

假设状态限定为：`待验证`、`暂时接受`、`已验证`、`已否定`、`不再使用`。模型状态限定为：`候选`、`主模型`、`辅助模型`、`备用`、`淘汰`。单条决策状态限定为：`proposed`、`active`、`rejected`、`superseded`。

当前状态必须出现在文件顶部的 `[!context]` callout 中。保留历史内容，但把失效项明确标记为 `superseded`、`已否定` 或 `淘汰`。

### 证据权威与数值副本

- 始终分开记录事实、假设、决策和结果；未经原始数据、可复现计算或可靠文献支持的内容不得升级为事实或结论。
- 重要结论至少链接一种证据：原始或清洗数据、代码、结果表、稳健性报告、图表或文献。
- 机器产物是数值权威源，分析卡、总览与交付物中的数字都是副本；每个副本都必须能回溯到具体文件、字段与聚合方式。
- 上游重跑后，先从权威产物重算，再同步更新全部副本。只更新一处副本属于未完成变更传播。
- 能从同一权威产物自动导出到交付阶段时，不手工抄写。

## 3. 最小充分上下文

按任务加载最少但完整的文件：

| 任务 | 必须加载 | 按需增加 |
| --- | --- | --- |
| 前期分析 | 赛题总览、数据理解、统一口径、当前分析卡、相关假设 | 题面原文、相关附件 |
| 模型实现 | 前期分析集合、当前模型决策 | 输入输出约定、验证与敏感性方案 |
| 结果解释 | 当前分析卡、统一口径、模型决策 | 结果 CSV、稳健性报告、图表、日志 |
| 论文写作 | 当前有效结论、统一符号、图表索引 | 最终模型理由、可靠文献 |

不要每轮加载整个 vault。不要把展示层文件当作源数据。

用户明确指定读取文件、章节或问题时，先遵守指定范围，再按直接依赖最小补读。开始工作前列出“指定读取、自动补读、未读取”及补读理由。

## 4. 冲突处理

不同文件冲突时按以下优先级判断可信度：

1. 标记为 `validated` 或 `active` 的当前决策（同一对象同时存在时优先 `validated`）；
2. 原始数据和可复现计算；
3. 已验证假设；
4. 当前问题分析卡；
5. 历史决策和旧结果；
6. 未验证猜测。

优先级只能帮助定位当前状态，不能替代证据核验。先列出冲突文本、来源、日期和下游影响；无法由证据解决时请求用户决策，不静默合并。

## 5. 变更传播

以下变化必须写决策日志并执行影响分析：

- 数据清洗、字段解释、单位或派生指标变化；
- G0.5 的目标或样本单位、预测/决策时点、可得字段或泄漏边界、划分、主指标及方向、预登记判据、核心权威产物或路线变化；
- 主模型、辅助模型或模型参数范围变化；
- 目标函数、约束、边界、插值或外推规则变化；
- 数据划分、验证方法或敏感性范围变化；
- 最终推荐方案变化。

影响分析至少覆盖：下游问题、需重跑代码、失效结果表、失效图表、项目总览和论文引用。旧证据不删除，只标记其适用版本或失效原因。

失效交付物按 `交付物清单.md` 中的条目逐条判定并标记为 `superseded`，不凭记忆笼统判断“某些内容要重做”。条目保留完整内容和失效原因，其吸收关系（`supersedes`）在重建条目时需要复核；图类同时复核面板与成稿目录。

上述 G0.5 契约或路线发生实质变化时，执行固定回滚：G0.5 置回 `not-checked` 并清空 route、reformulation 和当前 diagnosis_version；G1 记为 `blocked` 并清空 `unlocked_by`；问题退回 `stage: analysis`；原主模型退回 `候选`；逐条标记受影响结果、交付物与下游结论并列出重跑项。旧决定、旧诊断版本和证据保留。新诊断通过后生成新版本并重新执行 G1。纯措辞或无语义路径修正可不回滚，但须记录判断理由。

## 6. 决策来源与追加式记录

AI根据题面或数据提出的解释只是建议，不自动代表用户决定。每条口径建议至少记录：

- 提出来源：题面、数据、用户说明、可靠文献或AI建议；
- 题面/数据的字面含义；
- 字面含义的局限或劣势；
- 建议口径；
- 建议口径的优势；
- 支持证据、影响范围和当前状态。

AI建议默认使用 `proposed`。题面明确规定、证据唯一确定或用户明确确认后才改为 `active`。

用户未采用建议、以后改变决定或新证据推翻口径时，不删除或改写原记录。在同一决策条目下按日期追加：最终采用结果、决策理由、新证据、受影响文件和需重跑内容。根据结果将原建议标记为 `rejected` 或 `superseded`，但保留其完整论证，供论文解释模型口径选择。

对于不是语言口径的模型/方法决策，可将“字面含义”替换为“当前做法”，将“建议口径”替换为“建议调整”，仍执行同样的来源、优劣比较和追加规则。

## 7. Obsidian 约定

- 用 `[[文件名]]` 连接问题、数据、模型、决策和结果。
- 用 `![[图表.pdf]]` 或 `![[结果图.svg]]` 嵌入证据，不重复复制数据。
- 使用 `[!context]`、`[!fact]`、`[!assumption]`、`[!decision]`、`[!result]`、`[!warning]` 区分信息语义。
- Mermaid 只用于三节点以上的依赖、数据流、验证闭环或决策分支，不为简单关系强行绘图。
- 链接应指向真实存在或已明确计划创建的文件；重要结论不得只引用临时对话。

## 8. 阶段闭环

```text
题面与附件 -> 问题框架 -> 数据与统一口径 -> [G0.5 结构诊断] -> 路线
-> 模型候选 -> 验证与敏感性设计 -> 当前决策 -> [代码前门禁] -> 正式代码与实验
-> 结果回填 -> 稳健性判断 -> 项目设计总览 -> [论文前门禁] -> 论文
```

结论不稳健时返回模型候选，不直接润色成最终结论。项目设计总览只在项目中后期形成，用来展示最终主线，不替代原始分析卡、失败记录和决策日志。
