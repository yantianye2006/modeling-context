# 建模上下文执行流程

本文件是步骤 1–12、阶段推进和门禁动作的唯一流程来源。先在 `SKILL.md` 判定模式，只读取模式表指定的步骤；不要因打开本文件就执行全部流程。跨阶段状态、证据、冲突和变更传播仍以 `workflow-rules.md` 为准，结构诊断以 `model-diagnostics.md` 为准，其他方法细则以 `modeling-guardrails.md` 为准。

<a id="pipeline-step-1"></a>
## 1. 盘点证据与现有状态

1. 确认可靠题面、附件、已有代码、结果、图表和报告的位置。
2. 核对 PDF/扫描件中的公式、上下标、单位和字段，避免抽取错误改变模型方向。
3. 读取已有核心笔记顶部的 `stage`、`status`、gate 记录、当前上下文和未解决项。
4. 发现文件冲突时先列出冲突来源，不静默合并，不自行覆盖当前决策。

<a id="pipeline-step-2"></a>
## 2. 通过输入理解门禁

在初始化和分析前完成以下检查：

- 读懂题目核心目标、明确编号的顶层问题、输入、输出和关键定义。
- 对 `.xlsx`/`.xls` 附件调用可用的 spreadsheet 解析能力，以只读方式核对工作表、有效区域、表头、字段、单位、公式和数据类型；不得修改原文件。
- PDF 或 Excel 的渲染文件、抽取缓存、检查脚本和临时链接统一放入 `<project-root>/tmp/`，不得混入 `modeling/`。

如果无法确定子问题数量、关键公式、字段含义或附件结构，立即停止后续建模，告诉用户具体没看懂的文件、页码、工作表、单元格范围或术语，并请求解释。得到解释后再继续，不猜测补全。

如果 Excel 解析失败，报告解析器、文件、工作表和错误信息，并请求用户提供可读副本、CSV 或字段说明。若只有视觉渲染异常，但数值、表头和公式已通过其他只读检查核实，可记录视觉限制后继续；不得为改善预览擅自修改原 Excel。

<a id="pipeline-step-3"></a>
## 3. 初始化上下文库

### 输出位置

默认在项目根目录下创建 `modeling/` 作为 Obsidian 建模目录。**用户已有 vault 或已指定目录时，使用其实际位置，不另建目录。**先确定输出路径，再把它填进下面的 `--output`；不要因为示例里写着 `modeling/` 就在已有 vault 旁边平行造一个。

### 上下文库由哪些文件组成

```text
modeling/                     # 完整模式
├── 00_赛题总览.md            # GP 门禁记录在此
├── 01_数据理解.md
├── 02_统一口径.md            # 含图表 A/B/C 口径
├── 03_假设与风险.md
├── 问题1_分析卡.md           # 每问一份，G0/G0.5/G1–G3 记录在 frontmatter
├── 问题N_分析卡.md
├── 模型候选与淘汰.md
├── 交付物清单.md             # 图/表/规则/阈值/排程/方案的统一登记
├── 决策日志.md
└── 项目设计总览.md           # 门禁台账与预算台账由脚本派生
```

minimal 模式只生成 `00_赛题总览.md`、`01_数据与口径.md`、`02_问题分析卡.md`、`03_决策日志.md` 四份，问题章节与交付物登记内嵌在 `02_问题分析卡.md`，稳定章节 ID 与完整模式一致。

`深度学习候选.md` 是完整模式的扩展文件：只记录逐问题的深度学习适用性、残差优化价值、上游接口和下游结论支持，不并入 `模型候选与淘汰.md` 的传统模型树。

按题面明确编号动态确定问题数量，**不假设固定为三问或四问**；只把顶层编号问题视为子问题。

### 执行

确定输出路径和顶层问题数量后运行：

```powershell
python "<skill-dir>/scripts/init_modeling_context.py" --output "<实际建模目录>" --questions <N> --input-evidence "<题面、页码、附件或工作表证据>"
```

用户明确要求最小可行版本时增加 `--minimal`；有多条输入证据时重复传入 `--input-evidence`。只在输入理解门禁通过后初始化，脚本据此写入 `GP: passed`、检查日期和证据。非关键未知项可标为“待确认”；影响子问题数量、公式、字段语义或建模边界的未知项必须先询问用户。

旧上下文迁移前只运行预览：

```bash
python "<skill-dir>/scripts/preview_modeling_upgrade.py" --context "<project-root>/modeling" --deliverables --to-full
```

`--to-full` 只适用于 minimal；`--deliverables` 可单独用于旧《图表清单》。预览输出稳定章节映射、文件冲突和人工处理项，且不写入源目录。

<a id="pipeline-step-4"></a>
## 4. 建立问题框架

填写 `00_赛题总览.md` 和各 `问题N_分析卡.md` 的前五节：

- 每问的真实交付目标、输入、输出、约束和评价指标；
- 决策变量、状态变量或预测对象；
- 问题之间的数据流、模型依赖和仅用于解释的证据；
- 后续问题新增资源、约束或信息应产生的预期边际效果；
- 需要的结果表和图表证据。

先在分析卡 §1.1 画出最终答案的空骨架，明确字段、单位、粒度和使用方式；数值可以留空。再在 §1.2 逐条登记题面动词、对应交付物或必做分析及证据位置，避免只写“要分析什么”却没有定义最终怎么交。

用户明确要求赛事对齐、评审偏好或得分点，或提供了评分材料时，读取 `contest-alignment.md` 并在 §1.3 做对齐投影。本步只记录来源层级、与本题的映射、需要的交付证据和潜在失分风险；不生成候选模型、创新清单或完整解题报告。只有题面或正式比赛规则可以单独新增强制交付、改变 M1 或阻塞 G0；其他评阅信号仅作有来源的提醒。

交付物在此阶段只登记**需求**：根据 §1.1–1.2，在 `交付物清单.md` 中为本问所需的图、表、规则、阈值、排程或方案建立 `status: planned` 的条目，填写稳定 `id`、`kind`、`question` 和 `claim`，并把 ID 回填到交付物骨架。此时结果尚未产生，不虚构产物路径或验收证据。

同时在分析卡 §17 建立工作预算：M1 是本问题面的最低完整回答，至少包含主结论、基本验证和可使用输出；M2 是稳健性、基线、对照和重要敏感性；M3 是深化、扩展模型、额外解释或更昂贵实验。M1 的具体内容由 §1.1 交付物骨架和题型决定，不固定成“一张表”或“一次敏感性”。

只要任一问题缺少 M1 计划或仍有关键 M1 未完成，默认暂停与其依赖无关的 M2/M3。后续问题依赖该深化、验证决定主模型是否可用、用户明确调整优先级，或赛题权重与剩余时间给出充分理由时可以例外继续，但必须先在 `决策日志.md` 登记理由，并把条目链接填入“例外决策”。

先建立框架，再选择算法。如果题面含关键歧义，至少列出两种解释，通过简单验算、单位检查和问题递进关系决定当前解释。

<a id="pipeline-step-5"></a>
## 5. 建立数据事实源与统一口径

在 `01_数据理解.md` 中逐份登记附件、字段、单位、规模、缺失、异常、重复、分组和时间/空间结构。明确区分：

- 数据直接支持的事实；
- 数据不能直接确认的判断；
- 清洗或派生指标决策及其潜在影响。

在 `02_统一口径.md` 中统一符号、单位、核心公式、变量、目标函数、约束、评价指标、精度、边界、插值和外推规则。各问题不得私自采用冲突口径。

按 `modeling-guardrails.md`「目标可估性与数据支撑审计」填写分析卡 §6 的 G0 审计，核对目标量、观测机制、信息坍缩链、相关结构、基线难度和交付物要求的输出分辨率。不得用原始行数替代独立信息，也不得把单题经验阈值外推为通用禁令。

当问题框架、数据事实、统一口径和 G0 审计已经足以开始模型选择，且审计处置与交付物骨架一致时，将 G0 记为 `passed`，填写日期及所依据的分析卡、数据事实和统一口径证据，再将当前问题推进为 `stage: analysis`。审计未完成，或仍计划输出数据不支持的分辨率时，将 G0 记为 `blocked` 并填写具体缺口。仅创建了空白骨架时不得推进。

<a id="pipeline-step-6"></a>
## 6. 通过 G0.5 结构诊断与建模路线门

G0 通过后、冻结主模型前，读取 `model-diagnostics.md` 并填写分析卡 §6.5。先完成决策契约和竞争性结构假设，再选择最小充分探针，在观察结果前声明判据并生成 `criteria_hash`。把带时区秒级 `registered_at`、同一哈希和 `proposed` 状态追加到 `决策日志.md` 后，才可启动探针。

A 层探针是本问 M1 的必要前置，不适用 §4 的 M1 未完成时推迟 M2/M3 规则。它可作为 `stage: analysis` 内的受限诊断执行例外：代码与产物只服务 G0.5，写入 `<project-root>/outputs/diagnostics/` 或 `outputs/pilot/`；不得读取锁定测试指标、冻结主模型、正式大规模调参或冒充最终交付。需要复杂路线晋级、A 层不确定或形成高影响否决时，再按逐题预算进入 B 层。

每个已执行探针把真实数值、稳定 `evidence_id`、权威产物和 JSON run manifest 回填分析卡。只有以下条件全部满足，才把 G0.5 记为 `passed`：

1. 第 3 节所有适用探针均为 `executed` 并在第 5 节有完整数值；不执行者为 `not-applicable` 且写明理由与误判风险。
2. 每个结果行的权威产物和 manifest 都在 `outputs/` 下真实存在。
3. 决策日志预登记时间早于 manifest 的 `run_started_at`，分析卡、日志和 manifest 的 `criteria_hash` 一致。
4. `route`、`reformulation` 与核心证据、多指标取舍、否决路线、适用边界、G1 获准范围和重开条件完整；判定 `information_limited` 时 E1–E4 全部为“否”。

通过时填写新的稳定 `diagnosis_version`。证据不足或划分敏感时保持 `not-checked`，不设置 route；缺失必要数据、定义或外部条件时记 `blocked`。G0.5 未通过期间，`模型候选与淘汰.md` 中本问不得出现 `状态: 主模型`，G1 不得通过。同一算法跨问重复不构成缺陷；共享证据必须逐问登记共享机制、本问适用理由和反例风险。

<a id="pipeline-step-7"></a>
## 7. 设计模型、验证与失效边界

对每个问题至少明确一个直接回答题目的主模型；仅在承担解释、对照或独立验证职责时设置辅助模型。

每个候选模型必须说明的内容、验证划分与敏感性要求，执行 `modeling-guardrails.md`「模型表达」节的七项；参数来源、决策敏感性和断点/角点检查执行同文件「参数来源与决策敏感性」；题型专属防错项见「题型防错」。

把候选、主模型、辅助模型、备用与淘汰状态写入 `模型候选与淘汰.md`。淘汰记录必须保留原因、证据和下游影响，不删除历史；出现负结果时先登记事实，等结果回填后按 §11 选择闭环处置。

<a id="pipeline-step-8"></a>
## 8. 通过代码前门禁

只有当前问题同时满足以下条件，才可交给编程实现阶段：

- 输入字段、单位和可用范围明确；
- 输出、目标函数和评价指标明确；
- 变量类型、上下界和全部约束明确；
- 公式已清楚到可直接实现；
- 主模型与辅助模型职责不混淆；
- 数据划分、可行性检查、验证和敏感性分析已设计；
- 预期结果文件、图表数据和证据回填位置明确。

缺项时将 G1 记为 `blocked`，继续停留在分析阶段，并把同一缺项写入分析卡的“尚未解决的问题”和“下一步动作”。不要用代码替代尚未完成的建模定义。

除原有实现完整性外，G0.5 必须已经 `passed`；主模型必须处于 G0.5 的获准范围，G1 的 `unlocked_by` 必须等于当前 `diagnosis_version`。全部满足后，将 G1 记为 `passed`，填写日期和门禁检查证据；再将当前问题推进为 `stage: implementation`，刷新 `updated`，交给实现阶段。

<a id="pipeline-step-9"></a>
## 9. 通过具体方案与实验设计门禁

在输出具体最优条件、新实验坐标、调度方案或资源配置前，按 `modeling-guardrails.md`「具体实验与方案门禁」确认可行域，并按该节处理信息缺失，本节不另列一份清单。

无论是否读取了该 reference，以下两条始终成立：可行域未被确认前，不得编造具体点位，也不得把模型极值写成可执行方案；用户补充信息后才生成方案，并把补充来源与采用理由写入 `决策日志.md`。

需要输出具体方案时，缺少可行域就将 G2 记为 `blocked`；检查通过后记为 `passed` 并链接约束与方案证据。本问确实没有具体方案类交付时才记为 `waived`，填写理由和确认依据。G2 的变化不自动推进 `stage`。

<a id="pipeline-step-10"></a>
## 10. 记录决策并交接后续阶段

每次改变数据规则、假设、模型、目标函数、约束、验证方式或推荐方案时：

1. 更新对应文件顶部的当前状态；
2. 在 `决策日志.md` 登记本次决策，执行 `workflow-rules.md` §6「决策来源与追加式记录」；
3. 列出受影响的下游问题、代码、结果、图表和论文结论。

开始新的 M2/M3 工作前检查所有问题的 M1 状态；需要例外时先写决策日志，再把工作项推进为 `in-progress`。完成工作后更新 §17 的状态和证据，项目总览中的预算表只由校验器派生，不手工维护。

向实现阶段交接时，提供当前问题分析卡、数据与统一口径、有效假设、模型决策、输入输出和验证要求。不要把整个 vault 无差别加载给下游任务。

<a id="pipeline-step-11"></a>
## 11. 回填结果并闭环

代码或实验完成后，把关键指标、约束检查、结果表、图表、运行环境与复现方式、运行记录和稳健性报告链接回分析卡。结果不得只停留在终端或临时对话。

同时把 `交付物清单.md` 中相关条目由 `planned` 推进到 `drafted`，补全 `label`、`claim_source`、`source`、`artifact`、`acceptance`、`supersedes` 及 kind 专属字段。`supersedes` 必须如实列出被该条目吸收的旧条目；被列入者不得继续单独进入交付物。图类另补 `panels` 和 `caption`，其他 kind 不套用图表字段。

成稿图回填时，除登记路径与实测值外，**必须把产出图渲染回看一遍，并与上一版并排对比**，逐项确认 `02_统一口径 §图表口径` 的 B 类验收目标，结论写入条目的 `产物回看` 字段。**A 类断言全部通过不等于图可用**。只报告“断言通过”而没有回看记录，视为该图未完成。

明确记录：

- 结果属于事实、计算结果还是仍待验证判断；
- 主模型是否通过预设判定标准；
- 与预期不一致的现象、已知失败场景和适用边界；
- 相关假设转为 `已验证` 还是 `已否定`；
- 是否需要修改上游数据、假设、口径或模型，以及需要重跑的上下游任务。

每条淘汰或负结果必须在分析卡 §14 选择一种闭环处置：

- `替代方案`：说明改用什么及其证据；
- `缩小范围`：说明原结论仍在哪些场景可用；
- `负结论即答案`：说明为何“不存在显著改进”或“无法可靠估计”本身回答了题目；
- `未解决`：明确阻塞、下一步和对交付的影响。

外部文献、参考解或替代评价口径只能在预先说明可比对象与差异后用于对质，不得为失败结果事后挑选有利证据。只有 `未解决` 阻塞 G3；不得强迫每个有意义的负结论都换成另一个模型。

数值回填执行 `workflow-rules.md#证据权威与数值副本`。分析卡 §14 只登记权威文件、字段、聚合方式和当前副本值，不建立第二套规则。

主模型通过预设判据，或负结果已经以“缩小范围”或“负结论即答案”形成有证据的完整回答后，将当前问题推进为 `stage: validation`、`status: validated` 并刷新 `updated`。闭环处置为“替代方案”时先完成替代模型及验证；为“未解决”时返回模型候选与验证步骤，不得停留在 `validation`。论文前门禁通过前不得推进为 `writing`。问题卡的 `stage` 只反映本问进度，全局文件取各问的最低值。

若结论不稳健，返回模型候选与验证步骤；若稳定，更新 `项目设计总览.md`。随后运行校验器的 `--write-summary`，从 GP 和各问题卡刷新门禁台账，不手工维护该表。

本问出现“执行者是下游问题”的未完成动作时，除写在本卡 §17 外，同时登记到 `项目设计总览` 的「跨问题未完成动作」节。

若结果或上游变化触及目标、样本单位、预测时点、可得字段、泄漏边界、划分、主指标、预登记判据、权威产物或路线，先执行 `workflow-rules.md` §5 的 G0.5 回滚，不得继续沿用旧 G1。

<a id="pipeline-step-12"></a>
## 12. 通过论文前门禁

向论文、报告或其他交付物的写作阶段交接前，逐条确认：

1. 各问最终必须交付的结论、图、表、规则、阈值、排程或方案，在 `交付物清单.md` 中都有 `status` 至少为 `drafted` 的条目；§1.1 交付物骨架的每一行都能对应到已登记的条目 ID，§1.2 要求—证据追踪中不再有 `planned` 行；负结果闭环自检已完成且没有“未解决”处置；
2. 条目的通用字段和 kind 专属字段齐全，`source`、`artifact`、`claim_source` 边界清楚；
3. 交付目录中的每个文件都能反查到条目，活动条目的 `artifact` 也能定位到权威产物；
4. 每个活动条目的 `acceptance` 都有证据；`figure` 还须按 `02_统一口径 §图表口径` 填写 A 类实测值；
5. 每章成稿图不超过声明上限；超出时合并、删除或书面说明，非图 kind 不套用该上限；
6. 各问 §11.1 的参数敏感性与角点自检已记为 `passed` 或有理由的 `not-applicable`，高敏感参数已有扰动范围和证据；§14「数值来源」表已按当前产物重算，且交付物数值一致；
7. 每个活动条目完成 kind 专属验收：图有 `产物回看`，表有 `render_review`，规则/阈值有 `executable_check`，排程/方案有 `execution_precision`。

第 5 条实际约束图数；“每张图有理由”不能替代篇幅上限。第 4 条与第 7 条分别防止“口径写了没执行”和“只过机械断言却没有人回看产物”，两者缺一不可。

全部通过后将 G3 记为 `passed`，填写日期和七项证据；再把相关交付物条目冻结为 `active`，将对应问题推进为 `stage: writing` 并刷新 `updated`。任一条不通过时，将 G3 记为 `blocked` 并登记缺口，保持 `stage: validation`，不输出“可以进入论文阶段”。
