# Modeling Context

一个面向数学建模项目的可追溯上下文管理 skill。它帮助你在读取赛题、理解数据、选择模型、运行诊断、回填结果和准备论文交接的过程中，持续维护一套结构化、可验证的建模记录。

## 开源初衷

在 Agent 时代，与 AI 协同完成科研与竞赛已经是一件不可避免的事。然而在实际用 AI 做数学建模时，很容易遇到上下文断裂、研究过程失控、结论来源变成“黑盒”等问题。为了解决 **Agent 的上下文管理** 以及 **追溯研究过程、避免 AI 黑盒** 的痛点，作者开发了这个 skill。

## 作者的“建模哲学”

本 skill 的设计围绕以下三条核心理念展开：

1. **奥卡姆剃刀原则**：能用简单模型就不用复杂模型；当复杂模型没有稳定收益时，不再盲目升级。
2. **人是中心**：人应当对 Agent 进行主动引导，并知晓所有的技术细节，而不是把建模完全甩给 AI。
3. **预实验定路线，而非堆叠模型**：与其随意堆叠多个模型“炼丹比指标”，不如通过有针对性的预实验确定技术路线，对症下药，角逐出真正适合当前问题的方案。

## Skill 的核心优势

1. **统一管理的上下文，告别信息丢失**：建立结构化、统一管理的项目上下文，便于 Agent 随时掌握项目进度，不会因为上下文窗口切换或对话重启而丢失关键信息。
2. **全流程决策可追溯，打破 AI 黑盒**：让每一次决策都可以被记录——无论是失败的 idea 还是成功的方向都会留下痕迹。人和 AI 都能清晰理解项目演进脉络，彻底避免“论文写完却不知道结论是怎么来的”黑盒问题。
3. **以详尽分析与严谨门禁引导 AI 思考**：通过前置的问题分析流程与严格的新模型升级门禁，有效规避 AI 常见的两个通病：
   - **通病一**：对题目理解不深，只会给出“泛泛而谈”的通用模型推荐，缺乏针对性分析；
   - **通病二**：热衷于推荐华而不实的复杂模型（如动辄上神经网络、遗传算法等）。本 skill 通过升级门禁机制，确保只有证明具备明确优势时，才会解锁并采用复杂模型。

## 它解决什么问题

数学建模项目常见的问题不是“不会调用某个模型”，而是：

- 题面、附件和字段含义没有被系统记录；
- 数据口径、单位、时间范围和缺失值处理在项目中途悄悄改变；
- 还没有确认问题结构，就过早冻结模型或开始大规模调参；
- 诊断结果、模型选择和结论之间缺少证据链；
- 上游数据或假设变化后，下游代码、图表和论文结论没有同步失效；
- 代码输出没有登记为可回溯的权威证据。

`modeling-context` 将这些内容组织为一个有阶段、有门禁、有决策历史的建模上下文，适合与 Obsidian、代码仓库和论文写作流程配合使用。

## 核心能力

- 赛题总览、数据理解和统一口径维护
- 问题分析卡与项目设计总览
- 假设、风险、模型候选和淘汰理由记录
- G0、G0.5、G1、G2、G3 阶段门禁
- G0.5 结构诊断、A/B 探针和预登记判据
- 结果、图表、交付物和验证状态登记
- 决策日志与上游变更的下游影响分析
- 向代码、图表和论文阶段交接
- 用脚本初始化、校验、升级预览和生成诊断标准哈希

## 适用场景

它适用于：

1. 开始一个新的数学建模赛题；
2. 恢复一个已有但上下文不完整的建模项目；
3. 在正式建模前判断问题结构和信息是否足够；
4. 记录模型路线、验证方案和结果来源；
5. 当数据规则、假设或目标变化时分析影响；
6. 在代码、图表和论文之间进行可追溯交接。

它不能进行具体的计算，也不能进行论文写作、图表绘制。它只提供一个项目的上下文和工作空间

## 安装

将本仓库目录复制到 Codex 的 skills 目录，并保留以下结构：

```text
modeling-context/
├── SKILL.md
├── agents/
├── assets/
├── references/
└── scripts/
```

在 Codex 中可使用 `$modeling-context` 触发该 skill。具体安装位置取决于你的 Codex 环境；本机用户级安装目录通常是：

```text
~/.codex/skills/modeling-context/
```

## 基本使用方法

### 1. 初始化项目

准备一个项目目录，例如：

```text
my-contest-project/
├── problem/       # 题面和附件，只读
├── modeling/      # skill 维护的上下文
├── data/          # 工作数据或派生数据
├── code/          # 实现代码
└── outputs/       # 数值产物、图表和报告
```

然后在 Codex 中说明：

```text
使用 modeling-context 初始化这个数学建模项目。请先读取题面和附件，建立赛题总览、数据理解、统一口径和问题分析框架，不要直接选择最终模型。
```

初始化脚本位于：

```text
scripts/init_modeling_context.py
```

### 2. 恢复已有项目

```text
使用 modeling-context 恢复这个项目的建模上下文，先检查当前 stage、status、gate 和未解决事项，再只处理本轮指定的问题。
```

校验脚本：

```bash
python scripts/validate_modeling_context.py --context <project-root>/modeling
```

### 3. 进行结构诊断

当 G0 已通过、需要决定建模路线时：

```text
使用 modeling-context 对问题 2 进行 G0.5 结构诊断。请先登记诊断判据，再设计受限探针，保留条件候选，不要在 G0.5 通过前冻结最终模型。
```

G0.5 判断标准的规范哈希可通过以下脚本生成：

```bash
python scripts/hash_g0_5_criteria.py \
  --context <project-root>/modeling \
  --question 2
```

### 4. 回填代码结果

```text
使用 modeling-context 回填这次实验结果。请登记权威输出、数值来源、验证状态、适用边界，并检查它对问题分析卡和下游交付物的影响。
```

### 5. 分析上游变更

```text
统一口径发生了变化。使用 modeling-context 分析它对假设、模型、验证、图表、代码和论文结论的下游影响，不要覆盖历史决策。
```

## 工作流概览

```text
problem-framing
      │ G0
      ▼
analysis ── G0.5 ──► 路线确定与主模型解锁
      │ G1
      ▼
implementation ── G2 ──► 具体方案、实验或资源输出
      │ G3
      ▼
validation → writing
```

skill 只使用五个 stage：`problem-framing`、`analysis`、`implementation`、`validation`、`writing`。每个 gate 都应有明确的状态、日期和证据；历史决策追加记录，不静默覆盖。

## 设计原则

- 证据优先：不编造字段、数值、公式来源、运行结果或文献。
- 先理解后建模：输入结构、字段语义和问题数量不明确时停止建模。
- 诊断先于冻结：G0.5 通过前只保留条件候选，不冻结主模型。
- 历史可追溯：数据规则、假设、目标、约束、模型和验证改变时追加决策。
- 结果可重算：机器产物是数值权威源，笔记中的数值必须能回溯和重算。
- 探索与交付分离：调试图和探索结果不能直接冒充成稿交付物。

## 已知问题与局限

1. **跨平台兼容性未验证**：作者目前仅在 **Codex** 中实际运行过该 skill，其他 Agent harness（如 Claude Code、Cursor、Gemini CLI 等）对其适配情况尚未经过测试。
2. **严谨性与创新性的权衡**：预实验与升级门禁的路线设计本身没有问题，但在搭配部分比较保守的模型（例如 GPT 系列）时，一些本可能更有潜力的模型会因为初期某些指标表现不佳而被门禁拒绝升级。**如何在保持严谨性的同时兼顾创新性**，这一点作者仍在探索中，也诚挚欢迎社区朋友建言献策。

## 项目历史与作者自白

这是作者**第一个自主设计的 skill**，也是**第一个正式的 GitHub 开源项目**。受限于作者对 Agent 浅薄的理解和不算精湛的编程技术，这个 skill 看起来可能有些混乱，也不够规范。但即便如此，作者认为对于前文所讲述的设计目标和设计理念，它应当是能够胜任的——毕竟，它实打实地陪着我拿下了**国二**。希望各位大佬在使用时**取其精华，去其糟粕**。

项目最初的目的其实非常单纯，就是为了解决 Agent 的上下文管理问题；随后在实践中发现，单个大 `.md` 文件直接吃掉了 Codex 一大半的上下文窗口，于是痛定思痛进行架构改革。当时恰逢大学《人工智能概论》课程讲到了 Transformer 代替 RNN 以及 MoE（混合专家）架构，我便顺着“上下文路由”的思路，与 **GPT 5.5** 一起设计出了现在这套结构的雏形。

之后，项目又陆续经历了 **GPT 5.6 sol**、**Claude Opus 5**（P.S. 我的 Claude 帮我炼制完这个 skill 就封号归天了，这个 skill 成了 Claude 留给我最后的馈赠 😭）、**GPT 6 Astra** 的多轮打磨与修改；随着作者自己对 Agent 和 Workflow 理解的加深，又逐步加入了阶段升级门禁等机制。每一次修改，都离我心中对这个 skill 的设计目标更近一步。然而个人的认知总有局限，这也是我选择将它开源给社区的原因——希望能借助大家的力量进一步完善它，乃至超越它。

> 对我的第一个正式作品，我想说的真的很多，就像每一个开源玩家提交自己第一个作品时那样兴奋。感谢您阅读到此，期待您对这个 skill 的使用反馈、修改建议与 PR！
